## L1. 未リリースのサーバ機能を前提にしたクライアント側リファクタは、リリース確定まで着手しない

**発生**: 上流の新エンドポイントへ寄せてクライアントの重複実装を削る改修を検討したが、そのエンドポイントは本番未デプロイで、開発環境でも外部サービスへ到達できない状態だった。リリース時期が確定しない依存を抱えたまま、既存の動作する実装を消すことになる。

**ルール**: サーバ側の新機能に依存するリファクタは、**その機能が本番で動いていることを確認してから**着手する。「PRがマージ済み」「develop にある」は着手条件にならない。マージ済みとリリース済みは別。

**注意点**:
- 移行先が本番で動いていない間は、既存のクライアント実装を消さない。消すのはリリース確認後。
- 開発環境で「エンドポイントが 404 でない」ことは疎通の証明にならない。**実際の処理が最後まで通るか**を1件叩いて確かめる。
- togoid-lib-python の `tasks/lessons.md` L5 と同内容。両ライブラリで同時に踏むため両方に残す。

## L2. data.frame に対する `result[[1]]$col` は常に失敗する

**発生**: `togoid_label2id()` の既定は `format = "dataframe"` なのに、テストと README の例が `result[[1]]$identifier` を使っていた。data.frame の `[[1]]` は**最初の「列」**であり `names()` は NULL なので、この検査は移行前からずっと FALSE だった（テストは通っていたが何も検証していなかった）。

**ルール**: 既定の戻り値型を変えたら、テストと README の**取り出し方**まで追随させる。list 前提の `[[i]]$field` は data.frame では意味が変わる。

**注意点**: list 経路も残っているなら `format = "list"` の独立したテストを別に置く。片方の記法で両方を検査しようとしない。
